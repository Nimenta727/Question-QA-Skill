# Question bank / 题库格式 v1

UTF-8 JSON, one file per unit or subject (examples/sample_bank.json). Generate with an assistant, validate locally. The CLI DOES NOT make model calls or invent questions: its role is deterministic selection, grading, and recordkeeping.

Bank root: version (integer 1), subject (nonempty string), items (nonempty array).
Per item required: id (globally unique within a bank), concept (stable knowledge-point ID), level (recall/understand/apply/analyze/transfer), difficulty (1/2/3), type (single/short/manual), stem, claim, evidence, explanation, source (nonempty strings).
- single: options array of four distinct, nonempty strings and answer A/B/C/D.
- short: answer string and optional aliases string array. Only exact normalized matches are scored. Semantic equivalence must be added explicitly as an alias.
- manual: rubric array of nonempty criteria; result is entered by instructor/AI *after* rubric evaluation (score 0/0.5/1 plus reason).

The "claim" expresses intended mastery and "evidence" describes what the response demonstrates; "source" is a source anchor. Use traceable identifiers e.g. lesson-03:p12 or original-example:topic; DO NOT forge references. The answer and explanation are never returned by the 'next' command.

Limitations:
- The current CLI does not independently verify generated claims, ambiguous wording, multi-correct answers, or pedagogical fairness. The authoring audit is mandatory.
- The state file is bound to a byte-for-byte SHA-256 bank digest for the pending question. Changing a bank while pending requires restoring the original or running reset-pending (discard that unanswered prompt, without credit).
- State reports cover answered concept × level only; absence from a report means untested, not "mastered".
- Use separate state files per learner. Store no names or raw response text; keep state private and out of Git.
- Concurrent writes to one state path are not supported; use serialized sessions.


## Version 0.2 optional fields / v0.2 可选字段
- family: shared stable family identifier for paraphrases / near-duplicate variants. If omitted, defaults to the item ID.
- prerequisites: list of other concept IDs already present within the same bank.
- misconceptions: dictionary mapping each incorrect A/B/C/D choice to a reviewed misconception label. Correct-choice codes are invalid.

The state file additionally stores a short session ID, item family, response confidence, hint-used flag, level/difficulty/type and optional misconception tag. It never stores raw response text. All previous v1 bank fields remain required and unchanged. For reporting thresholds, see DIAGNOSIS.md.


## v0.4.0 — Student answer review and dashboard
- For manual items, a reviewer may supply one JSON entry per rubric criterion containing exactly: score (0, 0.5 or 1), evidence (nonempty text tied to the response), feedback (specific next-step guidance). The CLI averages rubric scores and stores numeric criterion_scores only.
- Manual review is **not an automatic semantic grader**; the reviewer must check the student's actual response before supplying score/evidence. Example structure in examples/sample_review.json (for demonstration only).
- For short answers, an independently reviewed semantic-equivalence override is possible using --review-equivalent together with --reason; never bypass multiple-choice answer keys.
- An offline bilingual summary HTML may be generated by scripts/dashboard.py using the bank metadata and private state. It never includes item stems, answers or raw response text.
- Protect the state JSON locally; do not commit real student histories to public repositories. See docs/INSTALL.zh-CN.md and docs/INSTALL.md.


## v0.5.0 — Optional numeric verification witness
For an objective numeric MCQ/short-answer item, add the optional field:

    "verification": {"kind":"arithmetic","expression":"(19-4)/3"}

scripts/question_quality.py will check that the explicit answer option/short answer has the exact Fraction-valued result, and reject a numerically equivalent wrong option. Only bounded arithmetic literals with +,-,*,/ are supported; no eval, function calls, variables, algebraic symbolic solving or evidence of curriculum validity. For nonnumeric questions, omit this field and rely on independent checked solutions.

The review template returned by --review-template contains the complete SHA256 of the bank's raw bytes and item IDs with all review claims false. --strict accepts only fully reviewed files bound to the same digest and with zero hard errors. This is auditable reviewer sign-off, not an automatic guarantee of pedagogical truth. See QUESTION_QUALITY.zh-CN.md / QUESTION_QUALITY.md.


## v0.6.0 optional independent student response adjudication
In addition to legacy --score/--reason and --rubric-judgments, manual question answers can be evaluated by --independent-reviews @file, optionally paired with --adjudication @file for disagreements. Two separate reviewers supply one score/evidence/feedback/verbatim-quote record per rubric criterion; their identities and independence are self-declared, not externally verified. Disputed scores require third reviewer arbitration before recording. --response-file reads a local answer without leaking raw text in shell arguments. Only numeric criterion scores, agreement rate and dispute count are persisted in state, not answer text, reviewer IDs or quoted evidence. Consult docs/ASSESSMENT.zh-CN.md.


## v0.7.0 optional math and state storage
Only short-answer questions may declare answer_equivalence with kind rational, or kind polynomial and variables ["x"], ["y"], or ["x","y"]. All expressions are subject to bounded safe exact arithmetic; no arbitrary code or general language grading. Unsupported mathematical syntax remains pending and requires manual review. See docs/MATH_EQUIVALENCE.md.

The local state format remains version 1. Alongside state.json are state.json.lock (persistent advisory lock path; do not unlink while active) and state.json.bak (the previous committed snapshot). Both contain or protect private learning history. See docs/STATE_SAFETY.md. The independent reviewer-study input/output schema is documented at docs/REVIEWER_STUDY.md.


## v0.8.0 state and appeal metadata
Each new response carries a stable opaque event_id. Older history events may be addressed by --event-index once to assign a stable ID. The optional state.appeals array records appeal_id, event_id, item_id, reason_code, status, timestamps, reviewer_confirmation_self_declared, decision, score_before and score_after. No original learner response or reviewer free text is persisted in this audit.

Five prior valid snapshots are retained in state.json.snapshots/ plus state.json.bak. Private full-state export requires two explicit confirmation flags; aggregate-only export is default and may still require privacy precautions. Deletion requires a typed confirmation and unlinks only managed local files, not remote copies. See docs/DATA_LIFECYCLE.md and docs/APPEALS.md.


## v0.9.0 authenticated appeal audit (optional)
Only a fresh state without previously opened appeals can opt into the local signed-review mode. state.audit contains a version, HMAC key identifier, reviewer registry identifier and sequential HMAC-linked entries for appeal openings/closures. Each entry commits to previous MAC, appeal snapshot and the corresponding event's effective score; state.json.audit-policy is a separate authenticated metadata marker. Secrets and real reviewer identity are NOT stored in this structure. External checkpoint receipts commit to chain length/head and can reveal replacement by older signed state if kept independently. The HMAC does NOT sign every non-appealed historical response. See docs/SECURITY_AUDIT.md.
